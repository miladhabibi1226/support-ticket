# مستندات سیستم مدیریت تیکت (Support Ticket System)

## ۱. روش اجرای پروژه
برای راه‌اندازی سیستم در محیط توسعه:

* **نصب وابستگی‌ها:** دستور `composer install` را در ترمینال اجرا کنید.
* **پیکربندی محیط:** فایل `.env.example` را به `.env` تغییر نام داده، اطلاعات دیتابیس را وارد کنید و `php artisan key:generate` را اجرا نمایید.
* **آماده‌سازی دیتابیس:** دستور `php artisan migrate` برای ساخت جداول و دستور `php artisan db:seed` برای درج داده‌های نمونه.
* **اجرا و مشاهده:** با دستور `php artisan serve` پروژه اجرا شده و می‌توانید با مراجعه به آدرس `http://127.0.0.1:8000` در مرورگر خود، رابط کاربری سیستم را مشاهده کنید.
* **نکته تست:** برای اجرای تست‌ها (php artisan test)، ابتدا یک دیتابیس جداگانه به نام `support_tickets_test` در MySQL بسازید. برای جلوگیری از هرگونه خطای محیطی، اطلاعات اتصال دیتابیس (نام دیتابیس، نام کاربری و رمز عبور) و همچنین `APP_KEY` خود را در **هر دو فایل** `.env.testing` و همچنین فایل `phpunit.xml` (در بخش `<php>`) تنظیم کنید تا تست‌ها بدون مشکل اجرا شوند.

## ۲. ساختار Database
این پروژه از دیتابیس MySQL استفاده می‌کند. جداول اصلی عبارتند از:

* **جدول `tickets`:**
ذخیره اطلاعات پایه تیکت شامل فیلدهای `total_open_seconds` (برای نگهداری زمان‌های پردازش‌شده) و `last_opened_at` (برای محاسبه زمان جاری).

* **جدول `ticket_status_histories`:**
ثبت لاگ تغییر وضعیت‌ها (فیلدهای `from_status`, `to_status`, `changed_at`) برای رهگیری دقیقِ زمان‌بندی‌ها.

* **مکانیزم کوئری:**
تمامی جداول از طریق Migrationها ایجاد شده‌اند و منطقِ پیچیده کوئری‌ها برای جستجو و فیلتر، در `scopeFilter` مدل `Ticket` پیاده‌سازی شده است تا پرفورمنس بهینه حفظ شود.

## ۳. معماری انتخاب‌شده
این پروژه از الگوی **Service Pattern** استفاده می‌کند تا منطق برنامه از کنترلرها کاملاً ایزوله باشد. این جداسازی باعث می‌شود کنترلرها «لاغر» (Skinny) و سرویس‌ها «چاق» (Fat) باقی بمانند:

* **کنترلر وب (TicketWebController):**
وظیفه این کنترلر دریافت درخواست‌های HTTP، اعتبارسنجی اولیه و انتقال داده‌ها به لایه سرویس است. نتیجه نهایی را به ویو بازمی‌گرداند تا منطقِ کثیفِ محاسباتی وارد لایه کنترلر نشود.
`app/Http/Controllers/TicketWebController.php`

* **کنترلر API (TicketController):**
این کنترلر به‌طور اختصاصی برای API طراحی شده است. تمام درخواست‌های ورودی کلاینت را به فرمت استاندارد JSON پاسخ می‌دهد و همان متدهای سرویس را فراخوانی می‌کند.
`app/Http/Controllers/Api/TicketController.php`

* **سرویس (TicketService):**
مغز متفکر سیستم. تمام منطقِ بیزینسِ پروژه (شامل محاسبات SLA، مدیریتِ لاگِ تغییر وضعیت‌ها و عملیات حساس) در این کلاس متمرکز است. این تفکیک باعث می‌شود منطق محاسباتی مستقل از فریم‌ورک و کاملاً قابل تست (Testable) باشد.
`app/Services/TicketService.php`

* **اعتبارسنجی (FormRequests):**
کلاس‌های `StoreTicketRequest` و `UpdateTicketStatusRequest` برای ولیدیشن‌های سمت کاربر به کار می‌روند.

* **رابط کاربری (UI):**
فایل‌های Blade که با Tailwind CSS طراحی شده‌اند. فایل اصلیِ نمایش لیست تیکت‌ها و فیلترها در مسیر زیر قرار دارد:
`resources/views/tickets/index.blade.php`

## ۴. منطق محاسبه Overdue
سیستم به صورت پویا وضعیت معوق بودن تیکت‌ها را بر اساس SLA زیر محاسبه می‌کند:

1. **شرط ورود:** تیکت باید دارای اولویت `high` باشد و وضعیت آن `done` نباشد.
2. **الگوریتم:** سیستم بازه‌های زمانیِ حضور در وضعیت `Open` را از جدول `ticket_status_histories` استخراج کرده و زمان‌های سپری شده در وضعیت `In Progress` را از کل زمان کسر می‌کند.
3. **نتیجه‌گیری:** اگر مجموع زمانِ خالصِ سپری شده در وضعیت `Open` از ۲۴ ساعت (۸۶۴۰۰ ثانیه) فراتر رود، تیکت به صورت خودکار به عنوان **OVERDUE** شناخته می‌شود.
